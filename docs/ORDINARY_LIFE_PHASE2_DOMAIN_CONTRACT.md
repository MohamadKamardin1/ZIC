# Ordinary Life Phase 2 Domain Contract

**Status:** Phase 2 complete — data dictionary, state machines, and lifecycle invariants defined

**Module:** Ordinary Life Insurance

**Delivery branch:** `sultan`

## 1. Purpose and design authority

This document converts the Phase 1 baseline into an implementation-ready domain contract. It defines the canonical vocabulary, ownership model, fields, relationships, states, transitions, invariants, security boundaries, audit obligations, and migration rules that Phase 3 must implement.

The workflow is grounded in the authoritative ZIC system specification [1], the existing Ordinary Life model surface [2], and the current lifecycle service behavior [3]. Existing field names are preserved where they are safe for compatibility, while target fields and model families are explicitly identified where the current implementation is too thin.

> The domain service is authoritative for business transitions. Serializers, admin forms, and frontend controls may collect or request an operation, but they must not bypass the transition rules defined here.

## 2. Canonical terminology

| Term | Locked meaning |
|---|---|
| **Partner** | The canonical external party in the existing Partner master. A Partner may be an individual, corporate customer, intermediary, employer, or service provider depending on its configured type. |
| **Policyholder** | The party that owns the contract and is responsible for contractual rights and obligations. |
| **Life assured** | The person whose life or insured event is covered. It may be the policyholder or a different eligible person. |
| **Payer** | The party that funds premiums. It may be the policyholder, employer, intermediary, or another permitted party. |
| **Beneficiary** | A person or entity entitled to a configured benefit, represented by an active allocation percentage. |
| **Intermediary/agent** | The partner or intermediary responsible for distribution and potentially commission entitlement. |
| **Product** | Stable business identity of an Ordinary Life offering. It is not itself a frozen calculation configuration. |
| **Product version** | An effective-dated, immutable-at-use configuration of a product. Quotes and policies reference the exact version used. |
| **Quotation** | A customer-facing quote identity containing one current version and historical versions. It is not a policy promise until approved and issued. |
| **Quotation version** | An immutable input and output snapshot for one calculation or material revision. |
| **Proposal** | A formal application created from one eligible quotation version, with declarations and underwriting context. |
| **Underwriting case** | The coordinated risk-assessment record for a proposal, including medical requirements and decision history. |
| **Approval** | A controlled decision by an authorized reviewer or generic approval engine. Underwriting approval and business approval remain separate facts. |
| **Commitment/payment allocation** | Evidence that an amount was received and allocated to a proposal or policy obligation. The future finance module owns the ledger; Ordinary Life owns the obligation context. |
| **Policy transaction** | A material financial or contractual event applied to a policy. Examples include issuance, endorsement, payment allocation, loan, withdrawal, surrender, paid-up conversion, reinstatement, renewal, maturity, and cancellation. |
| **Effective date** | The date on which a contractual or configuration change takes effect. Request date and approval date are separate facts. |

## 3. Identifier and common-field contract

Every new Ordinary Life entity uses a UUID primary key unless a shared platform convention requires otherwise. Human-facing numbers are generated by the existing numbering service and are immutable once assigned.

| Field | Type | Required | Contract |
|---|---|---:|---|
| `id` | UUID | Yes | Internal immutable identifier. Never exposed as the only human reference. |
| `*_number` | String | For operational records | Generated by a registered sequence, unique, immutable, and searchable. Examples: quotation, proposal, policy, receipt, endorsement, loan, withdrawal, claim. |
| `created_at` | DateTime | Yes | Server-generated creation timestamp. |
| `updated_at` | DateTime | Yes | Server-maintained update timestamp. |
| `created_by` | User FK | Recommended | Actor that created the record, when the record is user-created. |
| `updated_by` | User FK | Recommended | Actor that last changed the record. |
| `version` | Positive integer | For mutable aggregates | Optimistic-concurrency version incremented on successful aggregate updates. |
| `status` | Controlled string/lookup | For workflow entities | Must be one of the locked state values and changed only through a service operation. |
| `reason` / `comment` | Text | For material actions | Required for decline, cancellation, rejection, override, reversal, lapse, and manual adjustment actions. |
| `source_channel` | Controlled string | Recommended | WEB, API, ADMIN, PORTAL, IMPORT, BATCH, SYSTEM, or other centrally configured channel. |
| `correlation_id` | String | Recommended | Carries request/workflow correlation into audit and integration records. |

## 5. Relationship and ownership rules

The canonical aggregate roots are **Product**, **Quotation**, **Proposal**, and **Policy**. Related records are owned by the aggregate root unless the table is explicitly a shared reference or integration record.

| Aggregate | Owned records | External boundaries |
|---|---|---|
| Product | Versions, plans, benefits, riders, rates, underwriting and servicing configuration | Shared lookup/reference and system parameters |
| Quotation | Versions, selected benefits/riders, calculation trace, quote documents/notes | Partner master and optional intermediary |
| Proposal | Proposal parties, underwriting case, health/medical records, declarations, proposal documents/notes, payment obligations | Approval engine, partner master, document storage, payment/finance |
| Policy | Parties, benefits/riders, premium schedule/installments, status history, transactions, endorsements, renewals, servicing requests, policy documents/notes | Finance, commissions, claims, shared notifications/tasks, reporting |

Deletion is not permitted for a quotation, proposal, policy, payment, underwriting decision, transaction, or audit/history record once it has been submitted or used. Records are cancelled, expired, voided, reversed, or superseded through controlled operations.

## 6. State machines and transition contracts

### 6.1 Quotation

| From | Operation | To | Required conditions |
|---|---|---|---|
| `DRAFT` | Save revision | `DRAFT` | Creates or updates a draft version; no issued contract effect. |
| `DRAFT` | Submit | `SUBMITTED` | Active product version, valid partner, valid inputs, successful calculation, positive premium, and non-expired quote. |
| `DRAFT` | Cancel | `CANCELLED` | Authorized actor and reason. |
| `SUBMITTED` | Convert | `CONVERTED` | Quote is unexpired, partner is compliant, and selected quote version is complete. |
| `SUBMITTED` | Expiry job/action | `EXPIRED` | Expiry date reached and no conversion. |
| `SUBMITTED` | Cancel | `CANCELLED` | Authorized actor, reason, and no converted proposal. |
| `DRAFT`/`SUBMITTED` | Recalculate | same state with new current version | Old version remains immutable; new calculation passes deterministic validation. |

### 6.2 Proposal and underwriting

| From | Operation | To | Required conditions |
|---|---|---|---|
| `PENDING` | Start underwriting | `UNDERWRITING` | Proposal is complete and required declarations exist. |
| `UNDERWRITING` | Refer | `REFERRED` | Rule or underwriter requires senior/manual review; reason required. |
| `UNDERWRITING` | Approve underwriting | `APPROVED` underwriting decision | All requirements resolved or authorized override recorded. |
| `UNDERWRITING`/`REFERRED` | Decline underwriting | `DECLINED` | Decision reason and reviewer required. |
| `REFERRED` | Resolve referral | `UNDERWRITING` or decision state | Referral resolution and authority evidence required. |
| `PENDING` | Business approval | `APPROVED` proposal | Approved underwriting, required business checks, and authorized approval. |
| `PENDING`/`REFERRED` | Decline proposal | `DECLINED` | Reason required; terminal unless a new proposal is created. |
| `APPROVED` | Create payment obligation | `PAYMENT_PENDING` | Approved underwriting and business decision recorded. |
| `PAYMENT_PENDING` | Confirm first premium | `READY_FOR_ISSUANCE` | Settled allocation covers the required amount in the correct currency. |
| `READY_FOR_ISSUANCE` | Issue policy | `CONVERTED_TO_POLICY` | Issuance validations pass and no duplicate policy exists. |
| Any pre-issuance state | Expire/cancel | `EXPIRED`/`CANCELLED` | Rules and reason apply; no direct deletion. |

Underwriting and proposal approval are separate decisions. A proposal cannot become issuable because a user merely changes a status field.

### 6.3 Policy

| From | Operation | To | Required conditions |
|---|---|---|---|
| `READY_FOR_ISSUANCE` proposal | Issue | `ACTIVE` policy | First premium confirmed, issued snapshots created, schedules generated, and policy number assigned. |
| `ACTIVE` | Miss due premium beyond due date | `GRACE` | At least one unpaid installment and grace rules apply. |
| `GRACE` | Pay all required amount | `ACTIVE` | Allocation covers arrears and any configured charges. |
| `GRACE` | Grace expiry | `LAPSED` | Grace notifications and effective timestamp recorded. |
| `LAPSED` | Request reinstatement | `REINSTATEMENT_PENDING` | Within configured window and required evidence/payment submitted. |
| `REINSTATEMENT_PENDING` | Approve reinstatement | `ACTIVE` | Required arrears, medical review, and approval conditions satisfied. |
| `ACTIVE` | Apply endorsement | `ACTIVE` or configured result | Endorsement approved, effective, and transaction applied. |
| `ACTIVE` | Convert to paid-up | `PAID_UP` | Paid-up eligibility and calculation rules satisfied. |
| `ACTIVE` | Surrender | `SURRENDERED` | Surrender eligibility, value calculation, approval, and payable transaction created. |
| `ACTIVE`/`GRACE`/`LAPSED` | Cancel | `CANCELLED` | Authorized cancellation reason and financial impact recorded. |
| `ACTIVE` | Maturity | `MATURED` | End date reached, maturity conditions satisfied, and maturity transaction created. |
| Terminal state | Any normal lifecycle operation | prohibited | Only controlled reversal/correction process may be used, with audit and authority. |

### 6.4 Servicing request states

Endorsement, loan, withdrawal, surrender, paid-up, renewal, and reinstatement requests use a common pattern: `DRAFT → SUBMITTED → UNDER_REVIEW/APPROVAL_PENDING → APPROVED or DECLINED → APPLIED`, with `CANCELLED`, `EXPIRED`, and `REVERSED` where applicable. A request is not a policy change until its applied transaction exists.

### 6.5 Payment, loan, withdrawal, claim, and maturity states

| Workflow | States |
|---|---|
| Payment obligation | `OPEN → PARTIALLY_ALLOCATED → ALLOCATED → REVERSED` |
| Loan | `DRAFT → PENDING → APPROVED → DISBURSED → ACTIVE → PARTIALLY_REPAID → REPAID`, with `DECLINED`, `CANCELLED`, or `DEFAULTED` where configured |
| Withdrawal/surrender | `DRAFT → PENDING → APPROVED → PAYABLE → PAID`, with `DECLINED`, `CANCELLED`, or `REVERSED` |
| Claim linkage | Ordinary Life exposes coverage context; the future Claims domain owns claim states. Existing local claim compatibility states are `REPORTED → INVESTIGATING → APPROVED → PAID` or `REJECTED`. |
| Maturity | `PENDING → APPROVED → PAYABLE → PAID`, with `DISPUTED` or `CANCELLED` only through controlled action |

## 7. Lifecycle invariants

### 7.1 Identity, scope, and access

1. An acting user may only read or mutate a quotation, proposal, policy, or servicing record if the user has the required `ordinary_life.*` permission and can access the linked Partner through active partner links or an authorized system scope.
2. A partner-scoped user must not infer the existence of records belonging to an inaccessible partner through search, counts, validation errors, exports, or related-object endpoints.
3. Policyholder, life assured, payer, and intermediary relationships must be explicit; identity must not be inferred from display names or free-text fields.
4. Sensitive medical responses, financial records, and audit details require additional permission checks and must never be exposed through broad list serializers.

### 7.2 Product and configuration

1. Every submitted quotation resolves to exactly one active product version.
2. Product versions for the same product may not overlap in effective dates when both are active.
3. Product, benefit, rider, rate, underwriting, and servicing configuration used by a quotation or policy is immutable through that record’s lifecycle.
4. Inactive or future product versions cannot be used for a calculation unless an authorized effective-date rule explicitly permits it.
5. Age, term, sum assured, frequency, currency, and benefit selections must satisfy product-version limits before a quote can be submitted.

### 7.3 Quotation and proposal

1. A quotation version is immutable after creation. A material change creates a new version and updates the quotation current-version pointer atomically.
2. Quotation calculations are deterministic for the same normalized inputs, product-version snapshot, and calculation engine version.
3. Every submitted quotation must have a positive sum assured, positive premium, valid currency, valid term, valid frequency, valid parties, and a non-past expiry.
4. A proposal references one exact quotation version and cannot follow later quote revisions automatically.
5. A quotation can convert only once. Repeated conversion requests must be idempotent and return the existing proposal where safe.
6. Proposal submission requires required declarations and document/medical requirements determined by product rules.

### 7.4 Underwriting and approvals

1. Medical requirements are derived from versioned product rules and cannot be removed by a normal proposal update.
2. A proposal cannot be approved while required medical evidence is unresolved, unless an explicitly authorized override is recorded with reason and authority.
3. Underwriting approval, business approval, and payment readiness are distinct states and timestamps.
4. A decline or referral requires a non-empty reason and identified decision actor.
5. Approval authority is evaluated against the relevant sum assured, risk class, override, and user permission at decision time.
6. Underwriting decisions and medical evidence are append-only facts after issuance; corrections require a controlled reopen/correction operation.

### 7.5 Money, currency, and rounding

1. All monetary values use `Decimal`; floating-point arithmetic is prohibited in business calculations.
2. Every amount carries an explicit ISO currency code. Cross-currency operations require an approved rate and source timestamp.
3. Monetary fields are non-negative by default; amounts representing payments, benefits, and balances must be positive where the business operation requires value.
4. Rounding is applied only at defined calculation boundaries using one module-wide quantization policy; intermediate calculations retain precision.
5. Sum of installment amounts equals the schedule total after documented final-installment rounding adjustment.
6. Payment allocation cannot exceed either the payment receipt’s unallocated amount or the obligation’s outstanding balance.
7. A negative balance or over-allocation is rejected unless represented as a separately controlled credit/refund/reversal transaction.
8. A policy cannot be issued until settled payment allocations cover the configured first-premium obligation in the policy currency.
9. Loan outstanding balance equals principal plus accrued interest and charges less allocated repayments, with no silent direct edits.
10. Surrender, paid-up, withdrawal, maturity, and claim payable amounts are calculated from policy snapshots and approved rules, not client-submitted values.

### 7.6 Policy and servicing

1. A policy can be issued only once for a proposal and only from `READY_FOR_ISSUANCE` with all required snapshots and schedules.
2. Policy end date is after start date and reflects the product term unless a documented override is approved.
3. Every policy status change creates a status-history record, local workflow event, and central audit event in one transaction.
4. Every material policy change creates a policy transaction with an idempotency key, before/after state, actor/source, amount/currency where relevant, and external references.
5. Endorsements are effective-dated. A future endorsement must not alter current coverage before its effective date.
6. Endorsements cannot mutate the original issuance snapshot; they append a new version or transaction.
7. Active beneficiary allocations total exactly 100% for each benefit class that requires full allocation; percentages are positive and do not overlap in effective periods.
8. A policy cannot be surrendered, converted to paid-up, or withdrawn unless the product’s minimum duration, premium, and eligibility rules are satisfied.
9. Reinstatement is allowed only within the configured window and only after required arrears, evidence, medical review, and approvals are complete.
10. Maturity, surrender, cancellation, and paid-up states are terminal or restricted according to configured rules and cannot be casually reopened.

### 7.7 Audit, idempotency, and concurrency

1. Direct writes to status, premium, benefit, policy-party, payment, approval, medical-result, and transaction fields are restricted to domain services.
2. Every material service operation is atomic: state change, workflow event, audit event, task/notification hook, and related transaction either all commit or all roll back.
3. Repeated requests with the same idempotency key return the original result and do not create duplicate policies, payments, endorsements, or transactions.
4. Aggregate updates use optimistic locking or row locking where competing operations could create financial or state inconsistencies.
5. Central audit records are immutable. Before/after state snapshots exclude secrets and sensitive payloads unless the user has the appropriate audit authority and the field is required for compliance.
6. Workflow event history is append-only and cannot be deleted through normal APIs or admin.
7. System/batch jobs retain source channel, correlation ID, actor/system identity, and execution timestamp.

Report visibility remains separate from these action permissions. An authorized user may execute an action without automatically gaining access to every Ordinary Life report category.

## 9. Migration and compatibility constraints

1. Existing tables are evolved through additive migrations wherever possible. Destructive changes require an explicit data migration and rollback strategy.
2. Existing `OLProduct` records receive an initial product version representing their current fields before new quotes are required to use versioned configuration.
3. Existing `OLClient` records receive nullable Partner links. A data-quality report identifies unmatched clients; new submission paths reject unresolved identity unless a controlled migration exception is present.
4. Existing quotation, proposal, and policy rows receive compatibility snapshots populated from their current values. Historical records are never recalculated silently.
5. Existing status values are mapped into the locked state vocabulary through a documented migration table. Unknown values are preserved in a legacy field until resolved.
6. `OLCommitment` remains readable during the finance boundary transition. New issuance logic writes payment obligations and consumes allocation confirmations; legacy commitments are bridged rather than deleted.
7. Existing local workflow events remain queryable. New service operations write both local timeline events and central audit events until the local event is formally deprecated.
8. Migrations must pass Django checks, migration drift checks, existing backend tests, and data-integrity tests using both empty and populated databases.

## 10. Phase 3 implementation acceptance criteria

Phase 3 may begin from this contract. It must produce:

- A concrete schema migration plan for product versions, quote versions, parties, underwriting cases, policy snapshots, premium schedules, policy transactions, and compatibility fields.
- Database constraints and model validation for uniqueness, effective-date overlap, positive money, valid dates, beneficiary allocations, and required relationships.
- Service-owned write boundaries for lifecycle-critical fields.
- Explicit model constants/enums matching the state tables in this document.
- A migration-safe path for existing `OLClient`, `OLProduct`, `OLQuotation`, `OLProposal`, `OLCommitment`, and `OLPolicy` rows.
- Focused model tests proving the invariants before serializers and frontend screens are expanded.
